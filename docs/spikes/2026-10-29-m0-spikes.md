## 1. 结论

| spike | 判定 | 一句话 |
|---|---|---|
| S1-DSH 按帧 tail | **go，附一条例外** | 真实 DSH 会话 21 个事件，最多 0.79 s（100 ms 轮询）或 1.71 s（1 s 轮询）就能解出。例外在 DSH 自己：它攒 200 ms 再写，会话启动或后台写失败时会压得更久，语料里约万分之一的事件 >2 s，最长 5.1 s，读取方改不了 |
| S1-Codex 单帧 rollout | **go，有条件** | codex-cli 0.165.0 的 `codex exec` 运行时写的是明文 `rollout-*.jsonl`，按整行追加，不需要常驻解码器。写盘到可读 ≤720 ms，回合内事件到可读 ≤1.4 s。单帧 `.jsonl.zst` 是事后整文件压缩的归档（推断），只在冷读历史时流式解码 |
| S4 procguard | **go** | 系统 csc 编出的 helper 五个命令都跑通。杀掉 orchestrad 后，`ping -t` 孙进程和 dev server 0.93–1.42 s 内全部退出，0 幸存。嵌套 Job 随外层结束，Chrome/Edge 全在 Job 内，渲染器沙箱仍是 Lockdown |
| S5 Claude 根目录与等待信号 | **partial** | 等待信号存在：注册表 `sessions/<pid>.json` 的 `status=waiting` 加 `waitingFor`。SDK 宿主路径实测到，比审批请求早 0.33 s；Desktop 托管路径被动观察到。终端 TUI 路径没测到 |

S1-DSH 判 go 而不是 partial，是因为 go 判据要决定的是「用按帧 tail 还是用后备」。读取方在所有实测里都 ≤2 s；超时的那部分是 DSH 在写盘前压住的，projcache 后备只会更晚。r4 第 2365 行的验收要把这条例外写明。

S5 升级成 go 只差一步，需要你在场：开着 `spikes/s5-claude/passive-poll.mjs`，在一个已信任的目录里起一次终端 `claude`，让它触发一次 Bash 审批，最多 1 次模型调用。再在 Desktop 里碰上一次审批，正常使用中遇到就行。

## 2. 影响设计的发现

1. **便携 Node 24 带 Low 完整性标签。** `G:\_Projects\DSH-plugins` 目录上有显式的 Low 标签，`node.exe` 继承了它。在它上面跑的进程写草稿区报 EPERM，起的 procguard 只看得到约 13% 的进程。orchestrad 不能按 r4 第 585 行直接跑在这份 node 上（S4）。
2. **Node 拿不到自己 named pipe 的句柄。** Windows 上 Node 所有 stream 的 `_handle.fd` 都是 -1。管道对端的 pid + createTime 必须由 procguard 核实；「helper 扫描 orchestrad 句柄表」这条路已测通单连接，每次 0.2–0.5 s（S4）。
3. **Codex 活跃文件是明文，mtime 不动。** 写入期间 mtime 一直停在出生时刻，只有 size 在变，所以「最近 10 分钟修改过」要按 size 判断。rollout 比线程创建晚约 40 s 才出现，新会话要靠 `state_5` 发现。读取白名单要加上 `rollout-*.jsonl`（S1-Codex）。
4. **Claude 不装 hooks 也有等待信号。** SDK 和 Desktop 会话的「需要输入」可以从注册表直接做到 ≤2 s。`claude agents --json` 也能看到 `waitingFor`，但每次 4–35 s，而且会写根目录，Orchestra 不能调用它（S5）。
5. **DSH 默认上传会话日志。** `dsh-session-log-deepseek` 默认开启，会把会话日志增量随官方 DeepSeek API 请求一起上传；现有日志里有 7,890 条 delivery-accepted。Orchestra 拉起的 DSH 乐手也会上传，除非关掉。要交给 S2 和 §10.11 处理（S1-DSH）。
6. **DSH 帧比规格写的大。** 实测 77 B–1.4 MB，不是 83 B–62 KB。DSH 把 200 ms 内的事件攒成一帧再 fsync，58% 的帧有 2 条以上事件（S1-DSH）。
7. **procguard 修了两个漏洞。** kill-tree 曾接受打不开进程的 createTime 0；常驻模式下并发的 run-in-job 会把句柄漏给别人的子进程。都已修好并重测（S4）。
