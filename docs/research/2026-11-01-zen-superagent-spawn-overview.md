## 1 三家各是什么

| | Super-agent（DeepSeek） | Spawn | Orchestra r4 |
|---|---|---|---|
| 是谁的 | 一个团队、一个仓库的主动式同事 | 一整家公司，常驻 agent 舰队直接改线上产品 | 一个人在三家 harness 上的指挥台 |
| 活从哪来 | 外部事件：GitHub、飞书 | 约 60% 来自生产错误、bug 报告、日志和功能请求 | 你开的会话，以及你许的愿 |
| 怎么协调 | 一个 Router 分派，Worker 订阅 Thread 直接收后续消息 | 改共享环境（stigmergy），不互相广播 | 邮局：有向请求、回执、上限、来源追踪（r4 §8） |
| 谁能改规则 | **Router 用工具就能改**名单、准入表、接单模式和提示词 | 人；AI 裁判按先例裁定 | 只有你，在配对 UI 上改（D8：审批、拍板、刹车只能由你来做，超时即拒） |
| 什么算完成 | 没开 PR 的工单，执行器报 `ready` 就算完成 | 不审 PR：非作者 agent 挑错，每 15 分钟全量测试，按小时发布 | D19：任何 agent 都不能宣布完成，完成来自非作者复核者的判定或你的验收 |
| 不可逆动作 | 只靠提示词约束 | 少量硬编码门禁 | 人类动词只挂在配对 UI 上 |

## 2 三家共同的教训，用开眼准则看

1. **瓶颈从写代码移到了反馈、验证、决策。** Super-agent 说人一次只能跟 3–5 个会话。Spawn 的创始人有一天早上醒来，700 个问题在等他决策。r4 §2.2 的判断相同：瓶颈在会话之间的依赖，靠人转述撑不住。
2. **LLM 外面要有确定性层。** Super-agent 做得最好的地方是：LLM 要对每条规则逐条表态，判定落地那一刻再比一次策略版本。做得最差的地方是：评估者自己握着改评估标准的笔。Spawn 的裁判也一样：「退回」和「查先例给推荐」可以搬，「按先例直接裁定」与 D8、原则 2 冲突（原则 2：人是唯一的权威）。这两点都是 P8 的正反例（P8：权力靠递交，不靠够得着）。
3. **完成和失败都有口径漏洞。** Super-agent 没开 PR 的工单一报 `ready` 就算完成。Spawn 的 0.85% 回滚率不算靠叠加改动修好的故障。r4 也有一处同形的漏洞：假完成率不计「后来被别的 Task 弄坏的」，见 SP-2。这是 P1 和 P7 的问题（P1：完成只来自正证据；P7：规则就是测量，样本为 0 时显示「未测」）。
4. **只盯着「漏洞消失了没有」不够，还要检查核心路径仍然可用。** Spawn 的 Astra 为了修安全问题，把注册、创建和玩游戏都关掉了。r4 的愿望契约只写了「不得改动什么」，没写「什么必须仍然可用」，所以建议加 `invariants[]`，见 SP-1。
5. **环境协调和邮局不冲突，是分工。** 环境回答「现在是什么状态」，邮局回答「谁问谁、谁负责」。r4 已有不少环境协调手段：版本拒收、CAS（带版本号的比较后写入）、冻结测试、Decision 注入。缺的是一句分工说明，见 SP-7。还缺一条：污染不随仓库文件传递，见 SP-8。

## 3 本轮在本仓库代码里顺手核到的一处（M0）

Q-SA8 问「journal 格式怎么演进」。这一题在已提交的 M0 代码里已经部分有答案：

- `src/store/journal.ts:226`：遇到不认识的 kind，这一行就判为坏行；它后面只要还有 commit 行，就算链断裂，拒绝启动，不会截掉（`:150-153`）。
- `src/store/db.ts:285-290`：db 的 `user_version` 比本程序知道的新，就拒绝打开。

所以降级运行时数据是安全的。剩下一个 P1 问题（P1：需要你做不同动作的结局要用不同符号）：新版本写的记录被旧版本读到时，报的是 `journal-chain` 断链，和真正的文件损坏共用一个符号。可你该做的事完全不同，前者是升级程序，后者是去查盘、找备份。建议另起一个原因 `journal-newer`。这一点只读了代码，没跑测试。Q-SA8 的完整回答还要定 db 是从 journal 重建还是就地迁移：现在代码走的是就地迁移，迁移脚本在 `src/store/migrations/`。
