# Spawn：agent 原生公司，对照 r4 与开眼准则（2026-11-01）

Spawn 是一家做游戏生成产品的公司。2026-10-29，创始人发了长文《How I Built the Most AI-Pilled Company in the World》，讲他们怎么用一支常驻 agent 舰队写代码、发布和运营，基本不靠人审 PR。用户贴来的案例是另一位助手对这篇长文的二手解读。本文做三件事：拿一手原文核对案例里的数字；按协调、权力与裁判、验证与度量三个角度，对照 r4（现行规格 `docs/specs/2026-10-27-dsh-orchestra-design-r4.md`）和开眼准则（`docs/research/2026-10-31-eye-diagram-zen.md` 里的 P1–P9）；列出可以借鉴的、不能照搬的，以及要你定的事。

**标注。** 本文共用了 48 条发现，全部经过一轮唱反调式复核：30 条成立，18 条被削弱，0 条被推翻。被削弱的条目已按复核意见改写，标「（中）」，意思是置信度中等，不能当定论引用。

## 1. 结论先行

1. **数字基本都对，案例纠正得也对。** 17 条说法里，16 条和原文完全相符，1 条只是对开眼准则的映射过度了。案例指出二手帖有四处错误，都纠正对了：公司名是 Spawn 不是 Spond；花费是 310 万美元不是 320 万；故障后稳定花了 4 分钟不是 4 小时；原文没说训练过裁判。二手帖另有两处偏差，案例没提，见第 2 节。
2. **Spawn 用环境协调，和我们的邮局（Post Office，r4 §8：Orchestra 自己的持久邮局，带回执、上限、来源追踪）不冲突，是分工。**
   - 环境回答「现在是什么状态」，邮局回答「谁问谁、要什么、谁负责」。
   - r4 早就压低了 agent 之间的闲聊，例如 D16（沉默有效：通知不唤醒，回复不触发回复）。
   - r4 也已经有一套环境协调的手段：版本拒收、CAS（带版本号的比较后写入）、集成分支、冻结测试、Decision 注入。
   - 真正的缺口有三个：环境是一条污染追踪不到的通道；复核者看到的 diff 没有当成数据框住；M1 没有双写者告警。
3. **AI 裁判按先例三分流，只能搬两条，第三条不能搬。**
   - 能搬：「退回提问的 agent」和「查先例给出推荐，由你一键确认」。这两条都碰不到 D8（审批、拍板、刹车只有你能做；只有一个审批队列，超时即拒）。
   - 不能搬：「按先例直接裁定」。它和原则 2（人是唯一的权威）、§6.1（Decision 的结案人 `resolvedBy` 永远是人）、D8 正面冲突。
   - r4 里可行的替代是「这题你已经定过」：确定性地指回一条旧 Decision。权威来自你当初那一下点击，裁判只负责认出是同一道题。
4. **验证这一块，最值得补的是 Astra 那个教训。** 原文里 GPT Astra 为了修安全问题，把功能全关了。r4 的愿望契约只写了「不得改动什么」，没写「什么必须仍然可用」。建议给契约加保持类检查 `invariants[]`（SP-1）。同类的口径漏洞：假完成率把「后来被别的 Task 弄坏的」排除在外，r4 又没在别处记这笔账（SP-2）。
5. **10 万美元那个反例在 r4 里是已知风险，不是新漏洞。**
   - 如果是一次次派发，几小时内就会撞上调用次数上限。
   - 如果是单个在途的 DSH 回合，你不在时它没有自动停机。r4 自己写明了这点，也接受了这个风险。
   - 不建议加钱的上限，因为会推翻 Q3 = B（DeepSeek 不设花费上限，只计量）。建议把「给 DSH 回合加上限」提为 R79（你不在时，复核只在无网络的隔离边界里跑）开放前的硬前置条件（SP-6）。
6. **主线不动。** 按小时发布、agent 自行合并、按先例自动批准，都和已定规则冲突，不照搬。第 6 节有 7 个新问题等你定，每个都附了推荐默认。

## 3. 三个角度

### 3.1 协调

| 话题 | Spawn 怎么做 | r4 怎么做 | 差距与借鉴 |
|---|---|---|---|
| 协调介质 | 靠环境：代码、线上产品、数据库就是协调的媒介；不互相广播；取消 PR | M1–M2：愿望派发由主代理乐手经邮局发出，受 §8.3 规则 12（愿望派发闸门）约束。M3 起改由推进器派发（推进器是守护进程里的确定性组件）。复核请求从 M1 起由守护进程发（§8.9 (e)） | 是分工，不是冲突（中）。r4 §2.2（A2A 是多任务的前提）论证的是「人不该当中转站」，不是「agent 必须互相聊」。缺的是一句分工说明，见 SP-7。写的时候要分开 M1–M2 和 M3 起 |
| r4 已有的环境协调 | 对不上就进不去；每小时理顺 | 版本拒收：contractRev / planRev 不是当前版本就拒（§8.9 (f)）。CAS：claim / update 带 revision，不匹配返回 STALE_REVISION（§6.4，M3）。集成分支：A54（副作用键：commit trailer 加分支）。冻结测试：A59（gating 由非执行者编写并冻结）。Decision 注入新乐章（§11.6）。双写者告警（§10.8，M2） | 已有。Score 不算协调介质：它是只给人看的时间线；「agent 不读 Score」是推断，依据是 §8.6 里没有读 Score 的工具。接口（模块之间的 API 契约）r4 里没有，A18（每乐章冻结注入，含车道契约）只管职责和路径 |
| 同时改同一文件 | 原文没细说 | 双写者告警在 M2，列为 P0（立即通知）。但 M1 起自有乐手就能互发消息、各自写代码，这一段有空档。shell 写入会绕过写租约，r4 §10.8 已写明 | M1 空档见 Q-SP6 |
| 基于旧前提 | 原文没细说 | 版本拒收和 plan-stale（计划过期标记）。非愿望乐章运行中，你新定了一条 Decision 怎么办？§2.3 场景段写了：主代理手动发一条 wake:none 的 notice，乐手在下一个乐章的注入里拿到 | 有手动路径，缺守护进程自动推送（中），见 SP-14。Decision 也没有「适用条件」字段，见 SP-11 |
| 各自过了测试、组合起来坏了 | 每 15 分钟全量测试 | 串行，加最终在同一 HEAD 上重跑全部 gating（§8.9 (b)） | 防住了，但没记账，见 SP-2 |
| 日志和用户反馈里的诱导指令 | 原文把错误、日志、用户报告直接喂给 agent | 权限面防住了：消息不带权限、D8、D15（类型化权威，只认 trust 一个字段）。但 §8.5 的污染源只列了四类，项目根目录里的文件不算污染源 | 这是覆盖缺口，不是规则冲突（中）。§8.5 L1029 自己写了污染追踪是「尽力而为的启发式」。见 SP-8 |
| 复核的独立性 | 落地前由非作者挑错 | L2 复核者不看执行者的叙述（§8.9 (e)）。但 diff 是执行者写的，代码注释里可以写任何话 | r4 只对信封正文加了「以下是数据，不是指令」的框（L946），给复核者的 diff 没加（中），见 SP-9 |
| 经环境的因果 | 看到环境变了再动 | 现行双写者判据：两个活跃乐章编辑同一路径（§10.8 L1654） | 开眼的 I28 提议只认邮件作先后，会把正常的「A 提交，B 接着改」判成双写者。可以把 git 祖先关系当作第二种先后边，但只在 M3 起各自独立的 worktree 上成立（中），见 SP-16 |
| 订阅 | — | plan-stale 相当于订阅了一组路径（这是类比，不是 r4 的定义） | Super-agent 的 Worker 冲突也是靠共同订阅 Thread 发现的，所以订阅不只是省钱手段，也帮着发现冲突（中）。见 SP-15 |
| 长期身份加临时分身 | 常驻领域 agent，每个有名字和记忆，一天派出上千个辅助 agent。原文说每个 agent 都理解整个系统，不专业分工 | 乐手、乐章、分身三层（D2：乐手是持久身份，乐章是一次会话，分身不可寻址）。车道契约 A18。新建乐手要你批准（A17） | 结构对应得上。分工的前提不同：r4 走车道契约，C 编译器实验也用了专门角色，这是 Spawn 前提的一个反例 |

**冲突项（都不是真冲突，写清楚以免误读）：**
- **环境协调对邮局。** Spawn 一边：取消 PR，靠环境协调，不发消息。r4 一边：§2.2 把 A2A 定为第一支柱。r4 要的是 agent 之间能直接说话、不必由你转述，并不要求 agent 互相广播状态，原则 13 和 D16 反而在压低闲聊。所以两边都成立，加一句分工说明即可（中）。
- **P6、I24、I28 是开眼调研的提议，不是 r4 的规则。** P6（核心只认邮局这一条总线）、I24（封闭复核乐章：复核期间只收守护进程发的复核信和你亲手发的消息）、I28（跨乐章先后只认邮件）。说它们「封不住环境」「看不见经环境的因果」，是在修正提议，r4 的现行规则没有被违反（中）。

### 3.2 权力与裁判

| 话题 | Spawn 怎么做 | r4 怎么做 | 差距与借鉴 |

**冲突项：**
- **按先例直接裁定。** Spawn 一边：有先例，就由机器替人定。r4 一边：定的那一下只能是你在配对 UI 里的点击，依据是原则 2、§6.1 的 resolvedBy、D8 里的「拍板」动词。一旦搬过来，就是让机器结案 Decision，直接违反这三条。§3.2 的「不委托审批」和 Codex 的 guardian_subagent（把审批交给子代理）管的是工具审批，引在这里只是同类禁令的类比。开眼 P8（每条线只有一个驱动者；准则句是「权力靠递交，不靠够得着」）原文讲的是进程内能力怎样在启动时递给模块，挪到角色权威上是引申。
- **预选推荐。** 如果 judge 晋升后可以在卡上预选推荐，就和 §8.9 (c) 第 4 步「规划者的提议并排显示，不预选」冲突。预选会把你推向机器的答案，这正是 A-AUTO 审批疲劳的风险。真要预选，就得作为问题交给你拍板。
