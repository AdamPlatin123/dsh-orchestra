# 合奏：多层 agent 协作前端 mock 设计简报（2026-11-03）

写给 12 位以不同隐喻做 mock 的设计师。每人一个隐喻，但要解的是同一道题、用同一份剧本数据、过同一张自检表，这样用户才能逐个比较。

**一句话的题目。** 你（人）在一座 3~5 层的「乌龟塔」顶上：你 → 领头 agent → 它派出的 agent → 再派出的 subagent → ……。画面要让你**真正感觉到 agent 在合作**（谁把什么交给了谁、谁在等谁、谁回报了什么），同时**不被越来越多的对话淹没**，而且**派活、拍板、刹车的入口一眼就找到**。

> 本文自己的原则编号是 P1–P12，与研究笔记里「开眼准则」的 P1–P9、r4 通知分级的 P0–P3 都无关。通知分级在本文写作「通知级别 P0–P3」以示区分。

## 0. 产品背景（够用就行）

- **orchestrad** 是本机常驻的守护进程，页面只是它的窗口。它**观察**本机 Claude Code、DeepSeek Harness（下称 DSH）、Codex 三家的会话（只读），也能**开 Orchestra 自己拥有的** Codex / Claude 会话（可发消息、可审批、可停）。
- 会话三类归属（r4 D4：Orchestra 只驱动自己创建的会话）：**自有**（Orchestra 开的，可操作）、**只读**（三家自己开的，只能看）、**被占用**（别的程序正在驱动）。
- 塔的边有两种来源：原生的父子关系（subagent 挂在谁下面，靠文件位置，必然挂得上），以及 Orchestra 记录的派活与消息（你派的、agent 经 Orchestra 请求派的、乐手之间互发的）。DSH 会话装了 seat 插件后，可以**向 Orchestra 请求派一个 Codex / Claude 会话**，请求变成一张等你点「派出 / 拒绝」的卡，10 分钟不理自动拒。
- **人是唯一能派出、批准、拍板、刹车的一方。**（r4 D8：只有一个审批队列，超时即拒；这些人类动词只挂在配对过的浏览器页面上，agent 那一侧物理上没有这些按钮。）
- **诚实规则**（来自 alpha 0.1 设计稿，现写在 `shared/tower-contract.js` 注释里；r4 正文里没找到 T1–T3 这组编号，对应精神见 r4 §3.1 原则 7、11）：
  - **T1** 不知道写「未知」，不写「没有」，也不写成 0 或空闲。
  - **T2** 不用「完成」描述 agent 的工作。agent 不能宣布完成（r4 D19：完成只来自非作者复核者的判定或你的验收）；subagent 最远只到「已回报」。
  - **T3** 任何计数都等于它点开后那张列表的长度。
- **回报要薄**（r4 A16「薄完成」）：只给状态（由守护进程填：回合结束 / 到上限（写明哪一项）/ 被中断 / 出错）、有界摘要、引用；截断要标明。agent 自己的叙述只是附上的数据，永远不设定状态（r4 A55「算出的汇报，不叙述」）。

## 1. 现有前端为什么错（诊断，不是指责）

现有 `ui/tower.html`：顶栏（计数筛选、派活、解锁）+「等你」钉栏 + 按项目分组的树表 + 右侧详情 + 底部输入 dock。用户的评价是「完全错误」。拆开看，错在四处：

1. **单位选错了：一行一个会话。** 会话数随层数指数增长。真实数据里一次快照就有 135 个画出来的成员（24 个主会话 + 111 个 subagent），另有 718 个因上限被裁掉（`docs/research/2026-11-02-tower-panel.md` 末尾「第一步结果：真实数据抽样」）。树表把这些都当成同等地位的行，人只能逐行读。
2. **画的是从属，不是合作。** 树只表达「谁挂在谁下面」。合作是动词：派出、接手、回报、等待、复核、打回。这些在现在的界面上要么没有，要么藏在右栏的事件列表里。而且真实数据里 subagent 能对上「哪一次派活」的只有 2/111，所以即使画「谁派了谁」，98% 也是空的。
3. **动作散在四处。** 派活在顶栏的一个小按钮和「你」那一行；审批在钉栏和详情卡；对话输入和停止在底部 dock；DSH 请求卡在钉栏。用户找不到派活入口，就是这个问题的症状。
4. **诚实做到了，但用错了地方。** 「≈ 推测」「状态未知」「子·错·等」小框都是对的，但它们以表格列的形式铺满每一行，读起来是噪声。真实数据里 109/111 个 subagent 状态未知，于是满屏都是「未知」。

**要保留的好东西**（别在新方案里丢掉）：等你的事按离超时的远近排；计数可点开且等于列表长度；≈ 表示推测；「×12 Explore · 9 已回报 · 3 状态未知」这类聚合；三档停止（中断这一回合 / 结束会话 / 刹车整棵进程树）；没解锁时的占位卡（只知道哪一家、还剩多久）；高风险动作按住 1 秒确认；列表刚变过 750 ms 内点批准无效。

## 2. 人在这里每天真正要做的事（按频率 × 重要度排）

| # | 要做的事 | 一天几次（估） | 做不到的代价 |
|---|---|---|---|
| J1 | **扫一眼：有没有事在等我，最急的是哪件、还剩多久** | 几十次 | 审批超时被拒，agent 白跑；或者不停切窗口查 |
| J2 | **就地处理掉等我的事**：批准 / 拒绝一条工具调用，派出 / 拒绝一条 agent 的派活请求，回答一个提问，拍板一个决定。处理时要看到：谁要、要什么（参数全文）、它在哪条工作线上、是谁派它来的 | 十几到几十次 | 盲批（危险），或为了补上下文逐层点进去 |
| J3 | **发现卡住的**：谁卡住了，卡在等谁（等我 / 等另一个 agent / 等工具或外部 / 不知道） | 每小时几次 | 依赖链悄悄挂死，几小时后才发现 |
| J4 | **知道整体往哪走**：每条工作线（一个根任务或一个愿望及其整棵子树）进展到哪，用算出来的数（「3/7 已验证」），不用 agent 的自述 | 每天几次，离开回来时必看 | 被「全部完成！」骗，或完全没有全局感 |
| J5 | **派一件新活**：交给领头 agent（最常见）、指定某个 agent，或新开一个会话 | 每天几次到十几次 | 找不到入口，就回终端自己开，Orchestra 被绕开 |
| J6 | **看一条回报和它的证据**：回报说了什么、状态是守护进程填的哪一种、截断了没、引用指向哪（diff、日志、工具结果），复核结论是什么 | 每天十几次 | 只能信 agent 的话，或翻整段对话 |
| J7 | **刹车**：停一个回合、结束一个会话、杀一整棵进程树，并且事先知道会波及哪些子节点 | 罕见但必须秒级可达 | 跑飞的 subagent 吃掉内存或额度 |
| J8 | **进入某一个具体对话直接操作**（r4 Q0 已定 B：全部工作最终搬进乐手，每个乐手都要有你能进去直接操作的完整对话页） | 每天几次，持续时间长 | 被迫回原生 CLI |
| J9 | **离开再回来**：开会一小时回来，先知道这段时间发生了什么 | 每天 2~5 次 | 从头滚动每个对话 |

J1、J2 决定首屏；J3、J4 决定首屏的第二层信息；J5 决定入口位置；J6、J7、J8 决定「下钻」是什么样；J9 决定时间维度。

## 3. 从第一性原理推（设计师请先读这一节）

1. **注意力是唯一的稀缺资源，算力和 agent 不是。** agent 可以开很多，你的眼睛只有一双。所以首屏上每一个像素都要回答一个问题：它会不会改变你下一步的动作？不会的，退到背景或藏进下钻。
2. **对话数随层数指数增长，所以默认视图必须是压缩后的。** 一个领头 agent 派 4 个，每个再派 4 个，三层就是 21 个会话，五层是 341 个。首屏元素的数量必须随「等你的事 + 活跃工作线的数量」增长，**不能随会话数增长**。会话是存储单位，不是显示单位。
3. **人关心的是「责任在谁手上」，不是「谁在说话」。** 合作的本质是责任的移交：派出（我把事交给你）、接手、回报（我把结果交回）、等待（我的事卡在你那）、复核（另一个人判定你的结果）、打回。这些是**边上的事件**，不是节点上的状态。可感知的合作 = 看得见责任沿着边流动。
4. **合作有五种可感知的形态，每种都要一个视觉原语：**
   - **交接**（派出 → 接手）：一条有方向的边出现；带「谁派 · 何时 · 一句任务」。
   - **回报**（回报 → 被读 / 被采纳）：一个薄的包裹沿边逆流回到上级；带守护进程填的状态。
   - **等待 / 依赖**（A 卡在 B）：一条指向 B 的「等」边，带已等多久；链可以连成串，串的尽头才是真正要动的人（常常是你）。
   - **并行**（兄弟同时在跑）：同一层的多个活跃节点；压缩时是「4 在跑 · 2 已回报」这样的分项计数。
   - **复核 / 打回**（判定方与作者对峙）：作者与复核者之间的一条对向边，带结论（复核通过 / 没通过 / 没给出可用结论）和打回次数。
   - 另有一种**逆向请求**：下级向上请求资源（DSH 经 seat 请求 Orchestra 派会话），它沿塔**向上**到你这里变成一张卡。
5. **3~5 层不能靠缩进表达。** 缩进到第 5 层已经吃掉三分之一屏宽，而且越深的节点越窄、越难读。层级只需要被**完整看见一条**：当前焦点从根到叶的那条祖先链。其余枝叶都折成带计数的摘要。深度可以用位置、尺度、颜色深浅、地层、楼层、轨道……表达，但不能让每一层用不同的布局语法。
6. **需要你的事要冒泡，不要让你下钻去找。** 第 5 层的一条审批，应该在第 0 层就出现，并带一行压缩的来路：「Codex c-7（应 Ren 请求派出 · 属于 Lead 的愿望 W12）想跑 `pnpm vitest run api/export`」。你不必走进塔里，塔里要你的东西自己出来找你。
7. **真相规则必须落到视觉，而且三种置信度要三种画法。** 守护进程登记的（实）、从日志或文件修改时间推出来的（推测，≈）、不知道的（未知）——这三者必须一眼可分，且「未知」不能长得像「空闲」或「没有」。真实数据里未知占绝大多数，所以「未知」的画法必须**安静但不说谎**：不能吵（否则满屏警报），也不能消失（否则说谎）。
8. **安静是默认。** 正常运转的东西不占视觉权重；健康状态只在出错时出现。颜色和动效是预算，只花在两类东西上：等你的、出错的。动效只给「正在发生的交接」，并且可以关掉。

## 4. 原则 P1–P12

每条都带理由和一条可检验的标准。设计师的 mock 必须在页面里写明它「重押」哪 3~4 条、「放弃或弱化」哪条。

| 编号 | 原则 | 为什么 | 怎么检验 |
|---|---|---|---|
| **P1** | **显示单位是工作线，不是会话。** 首屏的一级元素是「工作线」：一个由你派出或你许下的根任务（或一个领头 agent）及其整棵子树。会话只在下钻后以个体出现。 | 第 3 节第 2 条：会话数指数增长，工作线数大致线性（你一天能发起的事有限）。 | 剧本「丰富态」里把 Aiko 下面的 Explore 从 12 个加到 120 个，首屏的元素数和布局不变，只有分项计数变。 |
| **P2** | **一个行动队列，按截止排序；在哪里点都是同一个对象。** 所有需要人的动词（批准、拒绝、派出、回答、拍板）汇在一个按剩余时间排的队列里，钉在固定位置。塔上、对话页里也可以出现同一个动作，但必须是同一个条目、同一个状态，处理一处另一处同步消失。 | r4 D8：只有一个审批队列，超时即拒；r4 §11.7：页内审批用同一个 UI 动词，收件箱为准。 | 剧本里 4 条等你的事全部在队列里，顺序是 6:10 的派活请求在 27:40 的审批之前；在塔上批准一条，队列里同一条立刻消失，队列计数减 1。 |
| **P3** | **需要你的事冒泡到顶，带一行来路。** 无论多深，等你的条目都在顶层出现，并附压缩的祖先链（谁 ← 应谁请求 ← 属于哪条工作线）。处理它不需要先展开塔。 | 第 3 节第 6 条。用户现在要逐层点进去才知道一条审批是谁派来的。 | 第 5 层（或第 4 层）的等你条目，在首屏可见、可直接处理，且显示它所有祖先的名字。 |
| **P4** | **每个没结束的节点都说清「在等谁、要什么」。** 等待对象只有五类：等你、等另一个 agent（写名字）、等工具 / 外部、在跑（不等谁）、不知道。等待可以连成链，链尾高亮。 | 卡住比出错更常见，也更难发现。r4 §11.2 要求标签写「在等谁、要什么」，不写内部状态码（借 Super-agent 研究 SA-6，见 `docs/research/2026-10-31-deepseek-superagent.md`）。 | 选中 Ren，能读出「等 Aiko 回信（已等 12 分）」；从 Lead 能顺着链读到「Lead ← Ren ← Aiko 正在跑」。 |
| **P5** | **合作画成边上的事件，不画成并排的头像。** 派出、回报、等待、复核、打回各有一种边或包裹的画法，有方向、有类型、有状态（在途 / 已到 / 已读 / 超时 / 被拒）。 | 第 3 节第 3、4 条。把 20 个头像排成一排只会让人觉得「很多人在」，不会觉得「它们在一起干活」。 | 不读任何文字，只看图形，能分辨出：哪条边是派活、哪条是回报、哪条是卡住的等待。 |
| **P6** | **焦点 + 上下文表达层级：一次只完整展开一条祖先链。** 选中任意深度的节点时，它的全部祖先同时可见；祖先的其它兄弟折成计数；不选时只显示到第 1~2 层。 | 第 3 节第 5 条。5 层全展开在任何隐喻下都会变成乱麻。 | 选中剧本里第 5 层的 grep-helper，屏幕上同时看得到 你 → Lead → Ren → Codex c-7 → reviewer → grep-helper 六个名字，且没有横向滚动。 |
| **P7** | **折叠必须诚实：聚合标签的分项之和等于总数，点开就是那张列表。** 例如「×12 Explore · 9 已回报 · 3 状态未知」，9 + 3 = 12，点开是 12 行。 | T3。折叠是压缩的主要手段，也是最容易说谎的地方。 | 剧本里每一个数字（队列计数、聚合标签、工作线进度、「自你离开」摘要）点开后的行数与数字相等。 |
| **P8** | **三种置信度三种画法；未知安静但不消失。** 实（守护进程登记）、≈ 推测（日志或文件时间推出）、未知，各一种视觉。未知不能与空闲、已结束、0 共用画法。 | T1；r4 §3.1 原则 7（解析失败降级为未知，绝不降级为错误状态）、原则 11（如实标注置信度）。 | 「贫瘠态」里 109/111 个 subagent 未知时，画面不暗示它们在跑或空闲，也不满屏报警；DSH 有 92 个会话但没读入时写「92 个，因上限未读入」，不写「没有会话」。 |
| **P9** | **回报是薄的、算出来的；永远不出现「完成」。** 回报卡只有：守护进程填的状态、有界摘要（标截断）、引用、复核结论；agent 的自述以引语形式附上并署名。进度用「n/m 已验证」，n 只来自复核或你的确认。 | T2；r4 A16、A55、D19。 | 全页搜索不到「完成 / Done / ✓ 完成」这类字样（「已回报」「复核通过」可以）；Lead 在对话里说「全部完成」时，工作线进度仍显示 3/7 已验证。 |
| **P10** | **派活入口永远在同一个显眼处，派活就是往塔上放一个新节点。** 入口在首屏固定位置、键盘可达（建议 `n`）；默认派给领头 agent，也可指定某个 agent 或新开会话；派出后新节点立刻出现在塔上，挂在「你」下面，带「你派 · 时间」。agent 发起的派活请求（seat）和你的派活入口在视觉上是同一件事的两面：请求在队列里等你点，点了之后结果长在塔上同一个位置。 | 用户原话：派活入口找不到。r4 §11.9 快捷键 `m` 给某个乐手发消息（记成派活标签）。 | 新用户进入首屏 5 秒内能指出派活入口；派出后不刷新、不切页就能看到新节点。 |
| **P11** | **人类动词带后果预览，并且只出现在能用的地方。** 刹车先预览波及范围（子树里几个会话、几个进程）；高风险批准要按住确认；只读会话上不出现批准、停止按钮，只写「在它自己的界面里处理」。通知和 toast 里永远不放「允许」。 | r4 D8、§10.9 审批规则、§10.5 场务刹车；现有三档停止的说明。 | 对 Kaito（只读会话）的 subagent 跑飞，页面给出的是「去 Codex CLI 里处理」与本机进程层面的刹车（受保护宿主要键入确认），不是批准按钮。 |
| **P12** | **时间维度用「自你上次看以来」，不用滚动的聊天墙。** 离开回来时，先给一段算出来的压缩叙述：n 条回报到达、m 条等你、k 个出错、哪些工作线前进了几格，每项可点开。实时流只在下钻进单个对话时出现。 | J9。r4 §11.2 的 30 分钟摘要与 §8.9 (h) 的晨报都是这个思路；把所有 agent 消息汇成一条时间流，正是「乱花渐欲迷人眼」的来源。 | 剧本「离开 12:58 → 回来 14:20」的摘要里，每个数字点开都等于列表长度，且摘要不超过一屏的五分之一高。 |

## 5. 设计上必须取舍的张力

每个 mock 都要在页面里写明它在下面每一对里站哪边、站多远。没有标准答案，这正是要逐个审阅的地方。

1. **合作可感 vs. 安静压缩。** 要看见责任在流动，但流动本身就是动静；动静多了就是噪声。
2. **空间隐喻的直觉 vs. 列表的可扫描。** 舞台、地图、楼层让人一眼有全局感，但扫 20 条等你的事，列表永远最快。
3. **全局（所有项目、所有工作线）vs. 焦点（一条线、一个节点）。** 两者能同屏到什么程度。
4. **实时 vs. 稳定。** 数据每 10 秒变一次，但人在读、在点的时候排序不能跳（现有规则：焦点在列表上时冻结排序，变化后 750 ms 内批准无效）。
5. **想象中的丰富数据 vs. 今天真实的贫瘠数据。** 丰富态里有派活边、A2A 消息、愿望进度；今天的真实数据只有 1 层深、98% 派活关系对不上、绝大多数 subagent 状态未知。好看只在丰富态里成立的方案，今天就会塌。
6. **隐喻的诗意 vs. 说人话。** 「延长记号 3」「错音 1」很美，但界面主文字必须是「等你 3」「出错 1」；隐喻术语只能做装饰或副标题。
7. **层级深度 vs. 屏幕宽度。** 5 层要放得下，1024 px 宽也不能横向滚动。
8. **压缩 vs. 进入对话直接操作。** 默认压缩，但用户要能一步进入任何一个自有会话的完整对话页并直接打字（r4 Q0 = B）。
9. **agent 的主动 vs. 人是唯一权威。** agent 会请求派活、会提议计划、会自述进度，界面要让它们的声音可见，但视觉上永远低于人的动作和守护进程算出的事实。
10. **只读会话 vs. 自有会话同屏。** 三家观察来的会话数量多、只能看；自有会话少、能操作。同一张图里怎么既不冷落前者、也不让人误以为能对前者下手。

## 6. 反模式（看到就扣分）

- **头像墙 / 多 agent 办公室**：每个会话一个同样大小的卡片或头像，网格排开。数量一多就是噪声，且不表达任何合作关系。
- **聊天墙**：把所有 agent 的消息汇成一条按时间滚动的流。
- **无限缩进的树**：第 5 层缩进到屏幕外，或每层都用相同权重展开。
- **绿勾「完成」**：任何形式的「Done / 完成 / All tasks completed」，包括把 agent 自述直接当状态显示。
- **未知变灰当空闲 / 写成 0 / 写「没有」**。
- **计数与列表不一致**：聚合标签分项相加不等于总数；顶栏数字点开后行数不同。
- **假忙碌动效**：粒子流、呼吸灯、跳动的思考气泡，表达「它在工作」却不对应任何真实事件。
- **常亮的健康面板**：一排绿灯、「所有系统正常」，占首屏位置。
- **通知里放「允许」按钮**，或在 toast 里完成批准。
- **派活入口藏起来**：只在菜单里、只在某行的详情里、只在没有派活记录时出现。
- **把推测画成实线**：没有记录的派活关系画成和有记录的一样的实边。
- **每层一种布局语法**：第 1 层是卡片、第 2 层是列表、第 3 层是气泡，人每下一层都要重新学怎么读。
- **隐喻术语当主文案**：「Fermata」「Wrong note」「Stagehand」作为按钮或计数的唯一文字。
- **拟人化情绪**：头像表情、颜色暗示「开心 / 焦虑」，误导成进度或健康信号。
- **对只读会话显示操作按钮**（批准、发消息、中断），哪怕是灰掉的。
- **审批批量按钮**：「全部允许」。r4 §10.9 与 §8.9 (h) 明确不做批量审批，每条绑定自己的请求摘要。

## 10. 候选隐喻（编排可改，每位设计师一个）

每个隐喻都要回答同一个问题：**它天然擅长表达合作的哪一种形态（第 3 节第 4 条），它天然会在哪条原则上失败。** 下面是候选和它们各自的考点：

| # | 隐喻 | 天然擅长 | 要小心的 |
|---|---|---|---|
| 1 | 乐团声部座位图（r4 §11.3 的 Stage） | 并行、声部分组、指挥台在前 | 头像墙；5 层在座位图里没有位置 |
| 2 | 分诊台 / 急诊分级 | 等你队列、按紧急度排、交接班 | 只剩队列，没有合作感 |
| 3 | 乌龟塔纵剖面 / 楼层 | 层级深度、冒泡到顶 | 每层一行会退回树表 |
| 4 | 地铁线路图 | 工作线 = 线路，交接 = 换乘站，等待 = 停站 | 线路多了像蜘蛛网 |
| 5 | 机场塔台 / 航班进离港大屏 | 截止倒计时、实时状态、稳定排序 | 只有列表，没有关系 |
| 6 | 厨房传菜口（出菜台 / 订单夹） | 交接与回报的物理感、谁在等哪道菜 | 难以表达 5 层 |
| 7 | 河流与支流 / 水系 | 回报向上汇流、分项计数是流量 | 方向和等待难画 |
| 8 | 邮局分拣 / 信件在途 | 消息在途、已读回执、薄回报是信封 | 变成消息流水账 |
| 9 | 作战沙盘 / 棋局 | 全局态势、焦点推进 | 过度游戏化 |
| 10 | 编辑部 / 报社排版台 | 稿件流转、复核打回、署名 | 看板列太多 |
| 11 | 电话总机（接线员） | 你是唯一能接通的人、请求上来要你插线 | 过于怀旧，难读 |
| 12 | 族谱 / 家谱卷轴 | 血缘、深层祖先链、聚合同辈 | 静态，缺时间感 |

也欢迎把两个隐喻嫁接（例如分诊台做队列 + 地铁图做塔），但要在说明块里写清哪部分来自哪个隐喻。
